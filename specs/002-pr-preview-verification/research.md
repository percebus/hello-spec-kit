# Research: Pre-merge preview and automated visual verification

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-10-28

Each entry resolves an unknown from the plan's Technical Context. Format:
Decision / Rationale / Alternatives considered.

## R1. Where the single shared preview is hosted

**Decision**: Publish the preview to GitHub Pages in a dedicated public
repository, `percebus/hello-spec-kit-preview`, served from its `gh-pages`
branch at `https://percebus.github.io/hello-spec-kit-preview/`. Each
deployment force-pushes one orphan commit that contains the static export plus
`.nojekyll` and `preview.json` (see
[contracts/preview-manifest.schema.json](./contracts/preview-manifest.schema.json)).
A fine-grained PAT, `PREVIEW_PAGES_TOKEN`, has **Contents: read and write**
access only to that repository.

**Rationale**:

- A repository has one Pages site and one deployment, so production cannot
  share it without overwriting production (FR-003).
- A second Pages site uses the production host, static server behavior, and
  base-path mechanism. Previews therefore catch the same class of bug as the
  motivating one: an image URL built from `NEXT_PUBLIC_BASE_PATH` in
  `app/about/page.tsx`.
- One fixed address naturally provides the single shared environment (FR-001,
  FR-002). It needs no third-party account, and the hosting is free for public
  repositories.
- `.nojekyll` is required because Jekyll would drop the export's `_next/`
  directory.

**Alternatives considered**:

- _Subpath of the production Pages site_: rejected because every Pages deploy
  replaces the whole site and couples preview to the `github-pages` production
  environment, violating FR-003.
- _Netlify, Vercel, or Cloudflare Pages_: these offer native per-PR previews,
  but add an external account, secrets, and code sharing with a third party.
  Their per-branch model is out of scope for this evaluation.
- _Only serve `out/` on the runner's `localhost`_: this is enough for the agent,
  but humans could not open it (FR-002, User Story 1), and it would not exercise
  real hosting.
- _`actions/deploy-pages` in the preview repo through `repository_dispatch`_:
  rejected because it adds a second workflow and cross-repo trigger with no
  benefit over a branch push.

## R2. Single-slot queue with latest-push-wins (FR-004, FR-006)

**Decision**: Put the whole verification workflow in one **workflow-level**
concurrency group, `preview-environment`, with `cancel-in-progress: false` and
`queue: max`. A first `resolve` job is the **staleness guard**. After the run
leaves the queue, it exits without deploying if the PR is closed, the PR head
moved past the run's SHA, or the PR is from a fork without maintainer dispatch.

**Rationale**:

- GitHub Actions officially supports `queue: max`, documented in "Workflow
  syntax › concurrency". It allows up to 100 pending runs in first-in,
  first-out order, so pushes to different PRs are never dropped. The default
  `queue: single` would cancel B's pending run when C pushes.
- gh-aw preserves the `queue` field in authored `concurrency:` blocks, as
  documented in the gh-aw concurrency reference.
- Workflow-level, rather than job-level, concurrency keeps the slot held from
  deploy through scan, agent review, and verdict. The preview therefore cannot
  change while a verification run uses it (FR-004).
- The staleness guard implements "a newer push replaces that branch's pending
  entry" and "closed PRs leave the queue". A superseded entry costs only a few
  seconds when reached. Commit statuses are per SHA, so an old commit's result
  never applies to a newer head.

**Alternatives considered**:

- _Default `queue: single`_: rejected because with three PRs it silently drops
  the middle one.
- _Per-PR group with `cancel-in-progress: true` plus a job-level global lock_:
  rejected because a job-level lock cannot span the deploy, agent, and verdict
  jobs.
- _A custom queue in an issue, label, or branch file plus a self-dispatching
  drain loop_: rejected because it duplicates a native feature and has race
  conditions.

## R3. Merge gate signal (FR-016, FR-018)

**Decision**: Use a single **commit status** with the context
`preview-verification` on the PR head SHA. A repository ruleset on `main` makes
it required, alongside the existing `Verify` check. A lightweight
`preview-enqueue` job in `always.yml`, which is not serialized, sets the status
to `pending` with a "Queued" message on every same-repo PR push (FR-005). The
verification workflow moves it through the states in
[contracts/commit-status.md](./contracts/commit-status.md).

**Rationale**: Job names generated by gh-aw are compiler-owned, and skipped or
superseded runs would create confusing check runs. One explicit status gives a
stable required-check name, an immediate "waiting" signal, and a single field
for the final verdict. If the check is missing or pending, merging is blocked by
default.

**Alternatives considered**:

- _Requiring the gh-aw job checks directly_: rejected because those names are
  not stable, and a stale run reports "skipped", which counts as passing.
- _Check runs API_: rejected because it requires a GitHub App identity to own
  the check. Commit statuses work with `GITHUB_TOKEN` and `statuses: write`.

## R4. Deterministic defect scan vs. agent judgment (FR-010, FR-011, FR-017)

**Decision**: Split the reviewer into two parts:

1. **Defect scanner** (deterministic, blocking): a new Playwright project,
   `preview-scan`, in the existing toolchain. Starting at the landing page, it
   crawls internal links under the base path at 320 px and 1440 px. It records
   the following as **blocking** findings:
   - same-origin requests that fail or return 4xx/5xx;
   - `<img>` elements that are not `complete` or have `naturalWidth === 0`
     after lazy content is scrolled into view;
   - `audio` and `video` elements with a `MediaError`;
   - `pageerror` events and `console.error` messages;
   - `documentElement.scrollWidth > innerWidth`, which means horizontal
     scrolling;
   - visible elements whose bounding box extends past the viewport, or that are
     clipped by an `overflow: hidden|clip` ancestor.

   It excludes elements that are 1×1 px or smaller (the visually-hidden
   pattern), descendants of intentional scroll containers, and text using
   `text-overflow: ellipsis`. For pages with findings, it captures full-page
   screenshots. External links get a short GET and, if they fail, an
   **advisory** finding. Output follows
   [contracts/findings.schema.json](./contracts/findings.schema.json).
2. **Agentic reviewer** (gh-aw, Copilot engine, built-in `playwright` CLI tool):
   - reads the PR, its diff summary, linked issues' acceptance criteria, and
     the scanner's findings;
   - navigates the preview from the landing page to the changed feature;
   - checks intent, with results reported as **advisory** per FR-017;
   - records other visual or usability concerns as **advisory** findings;
   - writes the verification report.

**Rationale**: The gate decision stays reproducible, while the agent still
provides the click-path reasoning and intent check the user asked for. Defect
categories are reliably detectable through browser APIs. AI judgment is
non-deterministic, so it does not decide merges, except that a run that never
finishes is inconclusive (FR-015). The scanner needs no new dependency and is
not limited by the agent sandbox.

**Alternatives considered**:

- _Agent-only review_: rejected because merge decisions would vary between runs
  and there would be no reproducible evidence for SC-003 and SC-004.
- _Visual regression snapshots_: rejected because they need baseline storage
  and maintenance, add many false positives on intended changes, and are not
  requested.
- _axe-core or Lighthouse_: rejected because they add new dependencies.
  Accessibility auditing is not in scope.

## R5. Agent sandbox, tools, and network

**Decision**: Use a gh-aw Markdown workflow, `.github/workflows/preview-verify.md`,
with:

- `engine: copilot`;
- `tools.playwright:` for `playwright-cli`, the CLI-only built-in tool;
- read-only `tools.github` toolsets `[pull_requests, issues]`;
- a restricted `bash` allowlist: `playwright-cli:*`, `jq`, `cat`, and `ls`;
- `network.allowed: [defaults, playwright, "percebus.github.io"]`.

The prompt pins the agent to `https://percebus.github.io/hello-spec-kit-preview/`
and forbids browsing production. PR, issue, and page text is wrapped as
untrusted data (FR-014), following the pattern in `issue-closed.md`.

**Rationale**:

- Current gh-aw uses `playwright-cli` instead of Playwright MCP.
- Domain access is controlled only by `network.allowed`.
- The repository already uses gh-aw, `COPILOT_GITHUB_TOKEN`, and
  `gh aw compile --validate`, as described in `.github/workflows/README.md`.
- gh-aw's AWF firewall and threat-detection job help defend against prompt
  injection.

**Alternatives considered**:

- _Custom Playwright MCP server_: rejected because gh-aw discourages it and it
  requires a manually pinned package.
- _Allowing the agent to browse production_: rejected because it is unnecessary
  and could confuse comparisons.

## R6. Recording the agent's verdict

**Decision**:

- The scanner job sets `preview-verification=failure` immediately when blocking
  findings exist. It is the only blocking signal.
- The agent ends by calling a custom safe-output tool, `record-verdict`, defined
  under `safe-outputs.jobs`, with `{ outcome: complete | inconclusive, reason }`.
  That job has `statuses: write` and is the only job that can set `success`.
  If the current status is already `failure`, it leaves the status unchanged.
  It sets `success` only when the outcome is `complete`; `inconclusive` sets
  `error` with the reason.
- A fallback `finalize` custom job uses
  `needs: [agent, detection, safe_outputs]`, `detection-gate: status-only`, and
  `if: always()`. If the status is still `pending` after the safe-output jobs
  settle, it sets `error` with "Inconclusive: reviewer did not record a
  verdict".

**Rationale**:

- A verdict passed through structured safe output is validated and processed
  outside the agent sandbox, so the agent never holds a write token.
- The fallback makes crashes, timeouts, and detection failures fail closed with
  a reason (FR-015, FR-018) instead of leaving the check pending forever.

**Implementation note**: If the compiler allows `finalize` to list the custom
`record_verdict` job in `needs`, do so. Otherwise, poll the status for up to
60 s before treating it as unset. Confirm this with
`gh aw compile preview-verify --validate`.

**Alternatives considered**:

- _Parsing a marker from the PR comment_: rejected because it is fragile and
  injectable.
- _Using workflow conclusion as the verdict_: rejected because it cannot
  distinguish "inconclusive" from infrastructure failure, and stale runs would
  succeed vacuously.

## R7. Report and screenshots (FR-012, FR-013)

**Decision**:

- The agent publishes one PR comment through the `add-comment` safe output
  with `target: "*"` and `max: 1`, following
  [contracts/verification-report.md](./contracts/verification-report.md).
- Scanner screenshots are uploaded as workflow artifact `preview-scan-<sha>`.
- The agent's screenshots use the `upload-artifact` safe output, limited to
  `/tmp/gh-aw/preview/*.png`.
- The report links to both artifacts and to the scanner's job summary.

**Rationale**: gh-aw recommends `upload-artifact` over `upload-asset`.
Artifacts keep evidence out of git history and expire automatically.

**Alternatives considered**: `upload-asset` was rejected because it writes
images to an orphan branch, which grows git history, even though it allows
inline images.

## R8. Making the preview visibly non-production (FR-002)

**Decision**:

- When the build sets `NEXT_PUBLIC_PREVIEW_PR`, `NEXT_PUBLIC_PREVIEW_REF`, and
  `NEXT_PUBLIC_PREVIEW_SHA`, `app/layout.tsx` renders a `PreviewBanner`: an
  `<aside aria-label="Preview build">` above the header showing PR, branch, and
  short SHA.
- `app/layout.tsx` also adds `robots: { index: false }` metadata in that case.
- Production builds leave these variables unset, so the HTML is unchanged.
- The deploy job writes `preview.json` with the same identity, so the workflow
  can wait for Pages propagation.

**Rationale**:

- Human visitors can tell immediately which PR is shown, which covers the
  shared-slot edge case.
- Search engines will not index the preview.
- The manifest gives a reliable readiness check, which is better than a fixed
  sleep.

**Alternatives considered**:

- _Rewriting HTML after the build_: rejected because it is brittle and could
  bypass static-export typing.
- _Titles only_: rejected because titles are not visible enough on mobile.

## R9. Untrusted builds and forks

**Decision**:

- `build` runs with `contents: read`, no secrets, and
  `persist-credentials: false`, and uploads `out/` as an artifact.
- `deploy` downloads that artifact and only pushes files. It never runs PR
  code, and it is the only job that sees `PREVIEW_PAGES_TOKEN`.
- Fork PRs are skipped by `preview-enqueue` and `resolve`. A maintainer can
  start a run for one with `workflow_dispatch -f pr_number=N` after reviewing
  its code.

**Rationale**: This follows least privilege and matches the spec's fork
assumption. GitHub also withholds secrets from fork-triggered `pull_request`
runs.

## R10. Override and rerun (FR-018, FR-019)

**Decision**:

- **Rerun**: run `workflow_dispatch` on `preview-verify` with input `pr_number`.
  It resolves the current head SHA and joins the same queue.
- **Override**: add a non-agentic `preview-override.yml` workflow, started with
  `workflow_dispatch` and inputs `pr_number` and `reason`.
  - It checks that `github.actor` has `admin` or `maintain` permission, using
    `GET /repos/{repo}/collaborators/{actor}/permission`.
  - It sets `preview-verification=success` with the description
    `Override by @actor: <reason>` (truncated to 140 characters).
  - It posts a PR comment with the full reason and a link to the run.

**Rationale**:

- The run log and PR comment are auditable and capture the reason.
- Ruleset bypass was rejected because it records who bypassed but not why.

## R11. Constitution alignment notes

- **Principle I (Static-only delivery)**: The preview is the same static export,
  only with a different base path.
- **Principle II (Simplicity first)**:
  - The plan adds no npm dependencies.
  - It adds three repository-level moving parts: the preview repository with
    its token, an agentic workflow, and an override workflow. Each is justified
    in the plan's Complexity Tracking.
  - Next.js predates this feature (ADR-001) and is not expanded.
- **Principle III (Accessible and responsive)**: The banner uses semantic
  markup, wraps at 320 px, meets contrast requirements, and is not a keyboard
  trap.
- **Principle IV (Verifiable in the browser)**: The feature makes browser
  verification automatic and mandatory before merge. The spec explicitly
  requests the automated scan.
